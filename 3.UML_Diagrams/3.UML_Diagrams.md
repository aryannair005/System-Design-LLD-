# UML Diagrams in Low-Level Design (LLD)

## 1. UML Basics

**Unified Modeling Language (UML)** is a standard visual language used to represent the structure and behavior of a software system through diagrams.

### Why Do We Need UML?

- Visualize classes, objects, and their relationships.
- Understand how objects communicate.
- Plan the code before implementation.
- Communicate design decisions clearly.
- Make complex systems easier to understand and maintain.

### Two Categories of UML Diagrams

**1. Structural Diagrams:** Represent the static structure of a system.

| No. | Diagram                     | Purpose                                         |
| --- | --------------------------- | ----------------------------------------------- |
| 1   | Class Diagram               | Classes, attributes, methods, and relationships |
| 2   | Object Diagram              | Objects and their links at a particular moment  |
| 3   | Component Diagram           | Software components and dependencies            |
| 4   | Composite Structure Diagram | Internal structure of a class or component      |
| 5   | Deployment Diagram          | Hardware nodes and software deployment          |
| 6   | Package Diagram             | Groups related model elements                   |
| 7   | Profile Diagram             | Customizes UML for specific domains             |

**2. Behavioral Diagrams:** Represent system behavior and interactions.

| No. | Diagram                      | Purpose                                |
| --- | ---------------------------- | -------------------------------------- |
| 1   | Use Case Diagram             | Actors and system functionality        |
| 2   | Activity Diagram             | Workflow or sequence of activities     |
| 3   | State Machine Diagram        | States and transitions of an object    |
| 4   | Sequence Diagram             | Messages exchanged over time           |
| 5   | Communication Diagram        | Interactions and links between objects |
| 6   | Interaction Overview Diagram | Overall flow between interactions      |
| 7   | Timing Diagram               | State or value changes over time       |

**Important:** For LLD interviews, focus primarily on Class Diagrams and Sequence Diagrams.

## 2. Class Diagram

A **Class Diagram** is a structural UML diagram that represents classes, their attributes, methods, and relationships.

### Class Structure

A class is represented by a rectangle divided into three sections.

```text
+---------------------------+
|          Student          |  Class Name
+---------------------------+
| - name: String            |  Attributes
| - age: int                |
+---------------------------+
| + study(): void           |  Methods
| + getName(): String       |
+---------------------------+
```

### Three Sections of a Class

- **Class Name:** Name of the class.
- **Attributes:** Data or properties of the class.
- **Methods:** Operations or behaviors performed by the class.

### UML Visibility Symbols

| Symbol | Meaning            | Java Equivalent |
| ------ | ------------------ | --------------- |
| `+`    | Public             | `public`        |
| `-`    | Private            | `private`       |
| `#`    | Protected          | `protected`     |
| `~`    | Package visibility | Default access  |

### Java Example

```java
class Student {
    private String name;
    private int age;

    public void study() {
        System.out.println("Studying");
    }

    public String getName() {
        return name;
    }
}
```

### Relationships in Class Diagrams

- Inheritance
- Association
- Aggregation
- Composition
- Dependency

## 3. Inheritance — IS-A Relationship

**Definition:** Inheritance allows a child class to acquire accessible properties and behaviors from a parent class.

It supports code reuse and establishes an **IS-A relationship**.

**Example:** A Dog IS-A Animal.

### UML Notation

A solid line with a hollow triangle pointing toward the parent class.

```text
+----------+
|   Dog    |
+----------+
     |
     |  ─────────▷
     |
+----------+
|  Animal  |
+----------+
```

The hollow triangle points toward the parent class, `Animal`.

### Java Example

```java
class Animal {
    void eat() {
        System.out.println("Animal is eating");
    }
}

class Dog extends Animal {
    void bark() {
        System.out.println("Dog is barking");
    }
}

public class Main {
    public static void main(String[] args) {
        Dog dog = new Dog();

        dog.eat();
        dog.bark();
    }
}
```

### Output

```text
Animal is eating
Dog is barking
```

### Key Points

- `Animal` is the parent class or superclass.
- `Dog` is the child class or subclass.
- `extends` establishes class inheritance in Java.
- The child inherits accessible methods from the parent.
- Java supports single inheritance of classes but allows implementing multiple interfaces.

## 4. Object Associations

**Definition:** Association represents a relationship between classes whose objects interact or are connected.

Three important relationships are simple association, aggregation, and composition.

### 4.1 Simple Association

**Definition:** Simple association represents a relationship between independent objects. Neither object necessarily owns the other.

**Example:** A Teacher teaches a Student. Both can exist independently.

### UML Notation

A solid line represents association.

```text
+---------+  1       0..*  +---------+
| Teacher |----------------| Student |
+---------+                +---------+
```

The numbers represent multiplicity: one teacher may be associated with zero or more students.

### Java Example

```java
class Student {
    String name;

    Student(String name) {
        this.name = name;
    }
}

class Teacher {
    void teach(Student student) {
        System.out.println(
            "Teaching " + student.name
        );
    }
}

public class Main {
    public static void main(String[] args) {
        Student student = new Student("Aryan");
        Teacher teacher = new Teacher();

        teacher.teach(student);
    }
}
```

### Output

```text
Teaching Aryan
```

### Key Points

- Objects are related but remain independent.
- Neither object necessarily owns the other.
- Association does not automatically imply lifecycle dependency.
- Java does not have a special keyword for association.

### 4.2 Aggregation — Weak HAS-A Relationship

**Definition:** Aggregation represents a whole-part relationship in which the part can exist independently of the whole.

**Example:** A Department has Teachers. Teachers can exist even if the department is dissolved.

### UML Notation

A solid line with a hollow diamond at the whole side.

```text
+------------+  ◇----------  +---------+
| Department |               | Teacher |
+------------+               +---------+
    Whole                        Part
```

The hollow diamond is placed at the `Department` end.

### Java Example

```java
import java.util.List;

class Teacher {
    String name;

    Teacher(String name) {
        this.name = name;
    }
}

class Department {
    private List<Teacher> teachers;

    Department(List<Teacher> teachers) {
        this.teachers = teachers;
    }
}
```

### Key Points

- Represents a weak HAS-A relationship.
- The part can exist independently of the whole.
- The whole refers to parts that can be managed independently.
- Java does not have a special aggregation keyword.

### 4.3 Composition — Strong HAS-A Relationship

**Definition:** Composition represents a strong whole-part relationship in which the part's lifecycle depends on the whole.

**Example:** A House owns Room objects in a simplified model. When the house is removed from that model, its owned rooms are removed from it as well.

### UML Notation

A solid line with a filled diamond at the whole side.

```text
+-------+  ◆----------  +------+
| House |               | Room |
+-------+               +------+
  Whole                    Part
```

The filled diamond is placed at the `House` end.

### Java Example

```java
import java.util.ArrayList;
import java.util.List;

class Room {
    private String name;

    Room(String name) {
        this.name = name;
    }
}

class House {
    private List<Room> rooms = new ArrayList<>();

    House() {
        rooms.add(new Room("Bedroom"));
        rooms.add(new Room("Kitchen"));
    }
}
```

### Key Points

- Represents a strong HAS-A relationship.
- The whole owns the parts.
- The part's lifecycle depends on the whole in the modeled design.
- Java does not enforce composition automatically; the programmer implements its ownership rules.

### 4.4 Difference Between Association, Aggregation, and Composition

| Feature      | Association            | Aggregation        | Composition        |
| ------------ | ---------------------- | ------------------ | ------------------ |
| Relationship | General connection     | Weak HAS-A         | Strong HAS-A       |
| Ownership    | Not implied            | Weak whole-part    | Strong whole-part  |
| UML Symbol   | Solid line             | Hollow diamond     | Filled diamond     |
| Lifecycle    | Independent, generally | Independent        | Dependent on whole |
| Example      | Teacher–Student        | Department–Teacher | House–Room         |
| Java Keyword | None                   | None               | None               |

### Important Interview Points

- All three can be represented using object references in Java.
- There are no dedicated Java keywords for association, aggregation, or composition.
- The distinction depends on ownership and lifecycle, not just the presence of a field.
- Inheritance represents IS-A; aggregation and composition represent forms of HAS-A.

### Quick UML Symbol Revision

```text
Inheritance:   Child ─────────▷ Parent
Association:   ClassA ───────── ClassB
Aggregation:   Whole ◇──────── Part
Composition:   Whole ◆──────── Part
Dependency:    ClassA - - - -> ClassB
```

## 5. Sequence Diagram

**Definition:** A Sequence Diagram is a behavioral UML diagram that shows how actors and objects exchange messages in chronological order to complete a task.

### Purpose

- Understand the flow of a use case.
- Identify which object calls which method.
- Visualize interactions between components.
- Plan method calls before implementation.

### Basic Structure

Time flows from top to bottom.

```text
Customer       App        PaymentService
   |            |                |
   |-- order -->|                |
   |            |-- pay() ------>|
   |            |<-- success ----|
   |<-- result -|                |
   |            |                |
```

### Key Points

- Participants appear at the top.
- Vertical dashed lines represent lifelines.
- Horizontal arrows represent messages.
- Messages are read from top to bottom in chronological order.

## 6. Sequence Diagram Components

### 6.1 Lifeline

**Definition:** A lifeline represents a participant throughout an interaction.

**UML Symbol:** A vertical dashed line.

```text
Customer
   |
   :
   :
```

**Example:** The lifeline of a Customer object during checkout.

### 6.2 Activation Bar

**Definition:** An activation bar shows the period when a participant is executing an operation or has control.

**UML Symbol:** A thin rectangle on the lifeline.

```text
Service
   |
   |  +---+
   |  |   |
   |  |   | Processing
   |  |   |
   |  +---+
   |
```

**Example:** PaymentService is active while processing a payment.

### 6.3 Synchronous Message

**Definition:** A synchronous message represents a call in which the sender waits for the operation to return.

**UML Symbol:** A solid line with a filled arrowhead.

```text
Client ------------> Service
          pay()
```

### Java Example

```java
paymentService.pay(500);
```

The calling method waits for the method call to return.

### 6.4 Asynchronous Message

**Definition:** An asynchronous message represents communication in which the sender does not wait for the receiver to finish processing.

**UML Symbol:** A solid line with an open or stick arrowhead in common UML notation.

```text
OrderService ----------> NotificationService
                 send()
```

### Example

An order service sends a notification request to a queue and continues processing.

**Important:** A normal Java method call is generally synchronous. Asynchronous behavior requires a suitable mechanism, such as an executor, message queue, or asynchronous API.

### 6.5 Create Message

**Definition:** A create message indicates that one participant creates another object.

**UML Symbol:** An arrow pointing to the beginning of a newly created participant's lifeline.

```text
Client --------> :Order
                 |
                 :
```

### Java Example

```java
Order order = new Order();
```

The object's lifeline begins at its creation point.

### 6.6 Destroy Message

**Definition:** A destroy message indicates the destruction or termination of a participant in the interaction model.

**UML Symbol:** An arrow pointing to a lifeline that ends in an `X`.

```text
Client --------> Session
                   |
                   X
```

**Example:** A session is explicitly terminated in a system model.

**Java Note:** Java does not provide a general `delete` operation for ordinary objects. Garbage collection reclaims unreachable objects; UML destruction does not necessarily correspond to a Java statement.

### 6.7 Lost Message

**Definition:** A lost message is sent to a receiver that is not shown in the diagram or is unknown.

**UML Symbol:** An arrow ending at an unknown endpoint.

```text
Sender -------->
          Unknown receiver
```

**Example:** A notification is sent to an external service whose internal behavior is not modeled.

### 6.8 Found Message

**Definition:** A found message arrives from a sender that is not shown in the diagram or is unknown.

**UML Symbol:** An arrow originating at an unknown endpoint and pointing to a known participant.

```text
              Receiver
                  |
Unknown --------->|
                  |
```

**Example:** An external payment gateway sends a callback to your application.

## 7. Complete Sequence Diagram Example

### Use Case: Customer Places an Order

```text
Customer       OrderService      PaymentService
   |                 |                  |
   |-- placeOrder() ->|                  |
   |                 |                  |
   |                 |-- pay() -------->|
   |                 |                  |
   |                 |<-- success ------|
   |<-- confirmation-|                  |
   |                 |                  |
```

### Corresponding Java Example

```java
class PaymentService {
    boolean pay(double amount) {
        System.out.println(
            "Payment processed: " + amount
        );
        return true;
    }
}

class OrderService {
    private final PaymentService paymentService =
        new PaymentService();

    void placeOrder(double amount) {
        boolean success = paymentService.pay(amount);

        if (success) {
            System.out.println("Order confirmed");
        }
    }
}

public class Main {
    public static void main(String[] args) {
        OrderService service = new OrderService();
        service.placeOrder(500);
    }
}
```

### Output

```text
Payment processed: 500.0
Order confirmed
```

The sequence diagram shows the order of interactions, while the Java code implements them.

## 8. Difference Between Class Diagram and Sequence Diagram

| Aspect        | Class Diagram                               | Sequence Diagram            |
| ------------- | ------------------------------------------- | --------------------------- |
| Category      | Structural                                  | Behavioral                  |
| Focus         | Static structure                            | Dynamic interactions        |
| Shows         | Classes, attributes, methods, relationships | Participants and messages   |
| Time Ordering | Not its focus                               | Central to the diagram      |
| Example       | Order contains order details                | Customer calls placeOrder() |

## 9. Quick Revision

- **UML:** A standard visual language for modeling software systems.
- **Structural diagrams:** Represent the static structure of a system.
- **Behavioral diagrams:** Represent behavior and interactions.
- **Class diagram:** Shows classes, attributes, methods, and relationships.
- **Inheritance:** IS-A relationship; hollow triangle points to the parent.
- **Association:** General relationship between objects.
- **Aggregation:** Weak HAS-A; hollow diamond; independent part lifecycle.
- **Composition:** Strong HAS-A; filled diamond; dependent part lifecycle.
- **Sequence diagram:** Shows messages exchanged over time.
- **Lifeline:** Represents a participant throughout an interaction.
- **Activation bar:** Shows execution or control.
- **Synchronous message:** Sender waits for the operation to return.
- **Asynchronous message:** Sender does not wait for completion.
- **Create message:** Indicates participant creation.
- **Destroy message:** Indicates participant termination.
- **Lost message:** Receiver is unknown or not shown.
- **Found message:** Sender is unknown or not shown.
